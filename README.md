# خَلِيّة — Khaleyya

منصة قرارات ذكية للمتاجر الإلكترونية. تطبيق Next.js (App Router) + TypeScript + PostgreSQL جاهز للنشر على Railway، بمصادقة حقيقية، وتحديد لمعدل الطلبات، وسجلّات منظّمة، وبنية جاهزة للربط الحقيقي مع اودو (Odoo) لاحقاً.

## البنية

- **الواجهة**: `public/dashboard.html` — نفس واجهة خَلِيّة الكاملة (لوحة التحكم، الخلايا العشر، القرارات، التنفيذ الآلي، غرفة الاجتماعات، التكاملات...)، مبنية بـ HTML/CSS/JS خفيف بلا إطار عمل، لكنها الآن متصلة بقاعدة بيانات حقيقية بدل بيانات وهمية في الذاكرة.
- **صفحة الدخول**: `/login` — صفحة React حقيقية.
- **الخادم**: Next.js API Routes تحت `src/app/api/*` — كل نقطة نهاية محمية بجلسة موقّعة (JWT + سجلّ جلسة في قاعدة البيانات قابل للإلغاء)، ومحدودة بمعدل الطلبات لكل IP.
- **قاعدة البيانات**: PostgreSQL عبر Prisma (`prisma/schema.prisma`) — كل الجداول مرتبطة بـ `storeId`، بحيث يسهل لاحقاً التوسّع لمتاجر متعددة دون إعادة كتابة المخطط.
- **التكاملات**: `src/lib/integrations/` — نمط "مزوّد" (`IntegrationProvider`) موحّد. كل منصة تعمل حالياً ببيانات تجريبية واقعية (`DemoProvider`)، مع مقبس جاهز لأودو (`OdooProvider`) يُفعَّل بتغيير قيمة واحدة (`ODOO_PROVIDER_ENABLED`) في `src/lib/integrations/registry.ts` متى قررت ربطه فعلياً.

## التشغيل محلياً

```bash
npm install --legacy-peer-deps
cp .env.example .env   # عدّل القيم بما يناسبك، خصوصاً DATABASE_URL و SESSION_SECRET
npx prisma db push     # يزامن المخطط مع قاعدة بياناتك
npm run db:seed        # يزرع بيانات تجريبية كاملة + حساب دخول أول (بريد/كلمة مرور من .env)
npm run dev
```

> **ملاحظة عن بيئة التطوير التي بُني بها هذا المشروع**: أثناء البناء في هذه الجلسة، كانت بيئة الحاويات السحابية تمنع تحميل ملفات محرك Prisma الثنائية من الشبكة (قيد خاص ببيئة الاختبار تلك فقط)، فتعذّر تشغيل `prisma generate`/`db push` واختبار الاتصال الفعلي بقاعدة البيانات محلياً هناك. تم فحص الكود بالكامل عبر `tsc --noEmit` و`next build` و`eslint` ونجح الاثنان تماماً بلا أي خطأ حقيقي (الخطأ الوحيد الظاهر هو غياب نوع Prisma المولَّد، ويختفي تلقائياً بمجرد تشغيل `prisma generate` في أي بيئة فيها اتصال إنترنت طبيعي — وهذا ما سيحدث تلقائياً أثناء البناء على Railway).

## النشر على Railway

المشروع جاهز بالكامل للنشر عبر `Dockerfile` مرفق (بناء متعدد المراحل، صورة إنتاج نظيفة وصغيرة). خطوات النشر:

1. أنشئ مستودع GitHub فارغ وارفع هذا الكود إليه (راجع القسم التالي).
2. أنشئ مشروع Railway جديد واربطه بهذا المستودع (`Dockerfile` سيُستخدم تلقائياً — ملف `railway.json` يحدّد ذلك صراحة).
3. أضف خدمة PostgreSQL من داخل نفس مشروع Railway.
4. اضبط متغيرات البيئة على خدمة التطبيق:
   - `DATABASE_URL` = `${{Postgres.DATABASE_URL}}` (مرجع تلقائي لخدمة Postgres في نفس المشروع)
   - `SESSION_SECRET` = قيمة عشوائية طويلة (32 حرفاً فأكثر) — يمكن توليدها بـ `openssl rand -base64 48`
   - `NODE_ENV` = `production`
   - `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `SEED_STORE_NAME`, `SEED_ADMIN_NAME` — بيانات حساب الدخول الأول (غيّرها عن القيم الافتراضية)
5. فعّل نطاقاً عاماً للخدمة (Generate Domain) من إعدادات Railway.

عند أول تشغيل، يقوم الحاوية تلقائياً بمزامنة مخطط قاعدة البيانات، ثم زرع البيانات التجريبية الكاملة (نفس ما هو معروض في النسخة التجريبية اليوم) إن كانت القاعدة فارغة، ثم تشغيل الخادم. أي عملية إعادة نشر لاحقة لا تكرر الزرع ولا تمسّ بيانات حقيقية أدخلها التاجر — كل خطوة زرع محمية بشرط "فقط إذا كانت فارغة".

## الأمان والإنتاج

- كلمات المرور مشفّرة بـ bcrypt (12 جولة).
- الجلسات: JWT موقّع (HS256) مرجعي لسجلّ جلسة في قاعدة البيانات — قابل للإلغاء فوراً (تسجيل خروج، تغيير كلمة مرور) بعكس JWT عديم الحالة التقليدي.
- كوكيز الجلسة: `httpOnly`, `secure` في الإنتاج, `sameSite=lax`.
- تحديد معدّل الطلبات لكل IP على كل نقطة نهاية API (نافذة منزلقة في الذاكرة — ملاحظة توسّع: بمجرد تشغيل أكثر من نسخة واحدة من الخدمة، يجب استبدالها بـ Redis/Upstash، والموضع الوحيد الذي يحتاج تعديلاً هو `src/lib/rate-limit.ts`).
- تسجيل أخطاء منظّم (pino) بلا تسريب لتفاصيل حساسة للمستخدم النهائي.
- رؤوس أمان HTTP قياسية (`next.config.ts`): X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.
- نقطة فحص صحة `/api/health` تتحقق من الاتصال الفعلي بقاعدة البيانات، لا فقط أن العملية حيّة.
- صفحة اللوحة الرئيسية (`/dashboard.html`) محمية عبر Proxy على مستوى الخادم (`src/proxy.ts`) — لا يمكن الوصول إليها دون جلسة صالحة، رغم كونها ملفاً ثابتاً.

## هيكلة قاعدة البيانات

كل جدول أعمال (`Cell`, `Decision`, `Automation`, `CellTask`, `ActivityItem`, `MeetingMessage`, `IntegrationConnection`) مرتبط بـ `storeId`، رغم أن المشروع اليوم يُشغَّل بمتجر واحد فقط مزروع تلقائياً. هذا قرار متعمّد: يسمح بتوسيع المنصة لاحقاً لتخدم عدة متاجر دون أي تغيير في المخطط — فقط بإضافة منطق تسجيل/تعدد مستأجرين فوق ما هو موجود.

## ربط اودو (Odoo) لاحقاً

كما طلبت، الربط الفعلي مؤجَّل لما بعد اكتمال الموقع. الجاهز الآن:

- `src/lib/integrations/types.ts` — الواجهة الموحّدة لأي مزوّد تكامل.
- `src/lib/integrations/odoo-provider.ts` — هيكل جاهز (stub) بتعليقات توضّح بالضبط ما يلزم تنفيذه (مصادقة JSON-RPC مع اودو، القراءة، الكتابة).
- `src/lib/integrations/registry.ts` — عند اكتمال `OdooProvider`، غيّر `ODOO_PROVIDER_ENABLED` إلى `true` فقط — لا حاجة لتعديل أي مكان آخر في الكود.
